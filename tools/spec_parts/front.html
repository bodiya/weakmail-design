§About this publication

This document publishes the complete technical characteristics of weakmail, so that anyone can build a transmitter, receiver or monitor for it from this text alone. It defines, normatively, the modulation (tones, symbol timing, modulation index, preambles), the frame format and every encoding used in it, the error-correcting code including the construction of its parity-check matrices and interleavers, the authentication tags, the mailbox protocol and the downlink waveforms, and it gives test vectors that pin every one of them to exact bits.

It is published before any on-air use, as the public documentation of the technique that 47 CFR §97.309(a)(4) refers to and that §97.309(b) and §97.113(a)(4) presuppose: a code anyone can decode does not obscure the meaning of a message. Nothing in weakmail is encrypted. Every header, every message body and every protocol field is sent in the clear in an encoding defined here; cryptography is used only to authenticate (Ed25519 signatures and HMAC tags appended to plain text) and to gate which station may ask a mailbox to retransmit a stored message. Anyone who receives a weakmail transmission can read it.

The sections numbered 0 to 7 and Appendix A are the specification itself, reproduced from the reference implementation's docs/SPEC.md with no change to the text. Where they name a file (weakmail/params.py, tests/...) it is a file of that reference implementation. Sections marked informative describe the reference receiver and its measured performance; a conforming receiver may work differently. The summary below and appendices E, R and V were added for this publication; their numbers are computed from the reference implementation's constants by tools/build_spec.py.

Status. Draft v1. The format is complete and implemented, and has been tested against simulated signals only; it is not yet in use on the air. Any change to what is transmitted will be published here, with a new version number, before it is used.
Open items in this draft, to be settled before the affected parts are used on the air:
  • Key-ups longer than 10 minutes. A single frame can take longer than the 10-minute identification interval of §97.119(a): {{LONG_KEYUPS}}. The callsign in such a frame's header cannot be decoded until the frame ends, and v1 defines no identification inside a burst. Until it does, a station should not send frames whose key-up exceeds 10 minutes.
  • Identification of sending stations. Every frame carries the sender's callsign (2.3), and mailboxes also identify in CW (4.12). Whether the header alone satisfies §97.119(b) for a handheld is discussed in Appendix R; a sending station can close each transmission with a CW or voice identification.
  • BEACON waveform (1.4). The on-off-keyed carrier is defined as a waveform only: its bit content, framing and identification are not specified. It is used for hardware tests and must not be used on the air as a weakmail transmission until specified. (The BEACON frame type of 4.13 is a normal frame and is fully specified.)

Anyone may implement this specification. The reference implementation (Python) and these pages (JavaScript, including a port of the encoder and receiver checked bit for bit against the reference) are free software under the GNU General Public License, version 3 or later.
