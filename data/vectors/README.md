# weakmail test vectors

Published, deterministic test vectors for the weakmail v1 on-air format (`docs/SPEC.md`).
They let an independent implementation check every stage of its transmit chain and its
decoder without running this code. Generated by `scripts/gen_vectors.py`; do not edit by
hand. `tests/test_vectors.py` regenerates them in memory and fails on any byte difference.

```
scripts/py scripts/gen_vectors.py            # regenerate after a deliberate on-air change
scripts/py scripts/gen_vectors.py --check    # exit 1 if vectors/ is stale
```

A diff in this directory means the bits on air changed. Commit it only on purpose, together
with the SPEC change that explains it.

## Files

| file | contents |
|---|---|
| `index.json` | tone plan, Gray map, class preambles, size classes, seeds; list of frame vectors; SHA-256 of every file |
| `keys.json` | the fixed **test** keys (Ed25519 seeds, public keys, key IDs), HMAC group key, challenge nonce, clock schedule (see the note below on `timestamp_min`) |
| `frame-NN-<name>.json` | one frame through the whole transmit chain (below) |
| `waveforms.json` | small reference-waveform windows (hash and exact statistics, not full files) |

**The keys in `keys.json` are public. Anyone can sign with them. Never configure them on a
real station.**

**`timestamp_min` means two things.** In a frame vector (`frame.timestamp_min`, below) it is
the **16-bit header field** (SPEC 2.1). In `keys.json`, `t0_min` and
`schedule.<frame>.timestamp_min` are the **full** minute count since the Unix epoch (e.g.
29000000), and the frame's header field is that count mod 2^16 (29000000 mod 65536 =
33088 in `frame-03`). `schedule.<frame>.mailbox_clock_s` is the mailbox's clock (Unix
seconds) when that frame is handled, `(full minutes) · 60 + 30`. A mailbox rebuilds the full
count from the field with its clock (SPEC 4.2 step 2), which is what the replay and
timestamp-window checks use.

## Frames

The vectors follow one complete mailbox session. The mailbox holds LoTW key bindings (SPEC
4.10) of K1ABC (originator), W9XYZ (recipient) and itself; bindings travel off air, so they
are not frame vectors. K1ABC submits the SPEC section 6 message to mailbox W1MBX, unsigned,
HMAC-tagged and Ed25519-signed, plus a UTF-8 variant. The mailbox ACKs. W9XYZ queries and gets
a LIST and a CHALLENGE. It answers with a RESPONSE, receives the DELIVER (the original
signed blob, byte for byte) and sends a signed delivery ACK. The mailbox then sends a BEACON.
Mailbox-originated frames are Ed25519-signed with the mailbox key, as
`weakmail.mailbox.protocol.Mailbox` does when it has a key. The test suite replays the session
through a real `Mailbox` and checks that it emits exactly these frames.

Every frame type a station or mailbox sends (SUBMIT, ACK, QUERY, LIST, CHALLENGE, RESPONSE,
DELIVER, BEACON) appears at least once; KEY is retired (SPEC 4.8).

## Frame vector layout

| key | meaning |
|---|---|
| `frame` | header field values (`type`, `src`/`dst` with their c28 values, `timestamp_min` = the 16-bit field value, flags, `body_kind`, `body_len`, `body` as text or hex) |
| `body_fields` | the control-frame body decoded per SPEC section 4 (msg_ids, LIST entries, nonce/digest, selector/signature, envelope, calls) |
| `auth` | tag kind and how to check it: signer + Ed25519 public key, or the HMAC key |
| `canonical_bytes` | `"WM1"` + header + body bits, MSB first, zero-padded: the signature input |
| `tag` | the authentication tag (empty when unsigned) |
| `msg_id` | SHA-256(canonical_bytes ‖ tag)[0:8] |
| `crc16` | CRC-16/CCITT-FALSE over header + body + tag bits |
| `info_bits` | header ‖ body ‖ CRC ‖ tag; `length` bits, packed MSB first (`hex`) |
| `size_class` | code length `n`, capacity `k = n/2`, `pad_bits` = zero bits after the tag |
| `coded_bits` | the LDPC codeword after interleaving (`tx[i] = c[perm[i]]`), packed MSB first, plus its SHA-256 |
| `tones` | per waveform class: preamble, number of symbols, key-up airtime, and the whole tone sequence (preamble first) as a string of tone indices 0-7 |

Bit strings are packed MSB first into bytes and zero-padded at the end to a whole byte; use
`length` to drop the pad. Tone `k` is at `1300 + 160 k` Hz. Data tones carry 3 coded bits
each, MSB first, label `v` sent on tone `GRAY_INV[v]`.

## Reference waveforms

`waveforms.json` covers the signed SUBMIT in each class, synthesised as in SPEC 1.8:

- IQ: `exp(j·1.5·sin ψ)` at 24 kS/s after 0.4 s of unmodulated carrier;
- audio: 0.4 s of silence, then `0.4·env[k]·sin ψ` at 48 kHz, where `env` is the discrete
  10-ms raised-cosine ramp of SPEC 1.6 (`env[k] = 0.5·(1 − cos(π(k + 0.5)/480))` over the
  first 480 samples of the tone burst, mirrored over the last 480, 1 elsewhere). This is the
  WAV `weakmail tx` writes. The audio `head` window includes the ramp, so its hash and sums
  reproduce only with exactly this `env`; the `data` window and the IQ windows have no ramp.

There are two 2-s windows: `head` (start of the key-up) and `data` (from the first data
symbol). Each window is quantised to int16 as `round(clip(x, -1, 1)·32767)` (IQ interleaved
I, Q) and gets the SHA-256 of its little-endian bytes plus exact integer sums, min/max, RMS
and the first samples. Integer statistics do not depend on floating-point summation order,
so they reproduce across platforms.
